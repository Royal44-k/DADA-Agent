# 哒哒 Agent ABCDE 分支根因分析与修复建议

## 结论

a、b、c、d、e 五个分支并非五个互不相关的问题。主要故障集中在两个公共环节：确认后的事务提交没有执行，以及工具失败没有约束最终回复。a 和 d 因确认态缺失而没有写库；c 和 e 随后只能查询到空结果；b 在空结果后仍允许语言模型生成“删除成功”，形成事实性误导。

## 测试范围和证据来源

测试通过 `http://192.168.5.19:8006/test_page.html` 与设备建立 WebSocket 会话。左侧交互日志用于核对每轮的路由标签、模型置信度、提示词阶段、工具参数、返回值和耗时。本文只保留脱敏后的必要证据，不包含原始 Token、完整提示词或用户隐私数据。

## a 分支 新建提醒

### 复现步骤

1. 输入“10分钟后提醒我检查测试报告，事项编号 CodexA0807”。
2. 系统询问是否确认创建。
3. 回复“对”。
4. 查询当前提醒。

### 日志证据

- 首轮 1.7B 路由到 `a/reminder_write`，置信度 0.999，耗时约 53 ms。
- 9B 正确抽取 `time_evidence=10分钟后`、`content=检查测试报告`、`recurrence=once`，耗时约 1232 ms。
- 系统生成一次确认话术，并把相对时间解释为 2026-08-07 16:48。
- 用户回复“对”后，1.7B 再次把该轮识别为 `reminder_write`，置信度 0.988，耗时约 55 ms。
- 9B 又执行一次槽位抽取，耗时约 910 ms，并重新生成确认话术；相对时间漂移到 17:11。
- 日志中没有 task 写库成功、主键、schedule 物化结果或 M9 同步记录。

### 根因

系统没有把第一轮确认请求保存为 `pending_operation`。第二轮的“对”被重新送入意图路由，模型只能再次理解为创建提醒，导致流程回到槽位抽取，而不是执行已冻结的写入命令。相对时间也在第二轮按当前时刻重新计算，因此发生漂移。

### 修复方案

1. 在会话层保存待确认对象：`operation_id`、`intent`、标准化槽位、绝对时间、创建时间、过期时间和幂等键。
2. 路由前先检查待确认状态。“对”“确认”“可以”直接进入提交；“不”“取消”清空状态；修改表达只更新对应槽位。
3. 第一轮解析相对时间后立即冻结为带时区的绝对时间。确认轮不得再次解析原始相对表达。
4. 数据库事务应同时完成 task 写入和首批 schedule 物化。只有事务提交后才能回复成功。
5. 成功日志至少包含 `operation_id`、`task_id`、生成的 `schedule_id` 数量、事务状态和耗时。

### 验收条件

- 确认一次只生成一个 task。
- 重复发送“对”不会重复创建。
- 从首次解析到最终写库，绝对提醒时间保持不变。
- 新建后立即查询能够返回该提醒。

## b 分支 删除或修改提醒

### 复现步骤

1. 输入“删除事项编号 CodexA0807 的提醒”。
2. 观察提醒查询、工具返回和最终回复。

### 日志证据

- 汇总日志一度显示 `chitchat`，置信度 0.789；同轮 1.7B 原始输出却为 `c`，耗时约 50 ms。
- 9B 在约 563 ms 后复判为 `reminder_modify`。
- 工具前置检查明确返回“用户当前没有任何提醒，无法修改或取消，不要再调用 reminder_modify”。
- 后续 9B 忽略该错误，生成“好的，已为您删除”。普通聊天生成器又输出一次“收到，已删除”。

### 根因

工具失败不是终止态，失败结果被当作普通上下文继续交给生成模型。最终回复没有绑定结构化业务结果，导致模型可以把失败改写为成功。日志还混合了首轮路由、二次复判和最终分支，无法确定真实执行路径。

### 修复方案

1. 工具统一返回 `status=ok|not_found|conflict|error`、`code`、`message` 和业务对象。
2. `status != ok` 时停止后续写操作和自由生成，只能使用与错误码绑定的失败模板。
3. 成功话术必须以数据库影响行数或已更新对象为前提。删除时要求 `affected_rows=1`。
4. 记录 `router_1_label`、`router_1_confidence`、`router_1_accepted`、`router_2_tool` 和 `final_branch`，禁止用单一标签覆盖全过程。

### 验收条件

- 无匹配提醒时只能回复未找到，不能出现删除成功。
- 有多个候选时必须消歧，不能默认删除。
- 删除成功后查询不到目标，其他提醒不受影响。

## c 分支 查询提醒

### 复现步骤

输入“我现在有哪些提醒？”。

### 日志证据

- 1.7B 路由到 `reminder_query`，置信度 0.998，耗时约 58 ms。
- 返回“当前没有提醒”。
- 同期 `schedule_sync` 消息中的 `entries` 为空数组。

### 根因

c 分支的空结果与当前数据库状态一致，但该状态是 a 分支未提交造成的。现有日志没有说明查询范围、用户标识、task 数量、schedule 数量和过滤原因，因此尚不能单独证明 c 完全正确。

### 修复方案

1. 先修复 a，再执行新增即查和跨连接查询。
2. 查询日志记录 `user_id_hash`、查询条件、task 命中数、schedule 命中数及过滤计数。
3. 将“无数据”和“查询失败”分成不同状态与话术。

### 验收条件

- 新建提醒后立即可查。
- 断线重连后仍可查。
- 已取消、已删除和过期记录按产品规则过滤。

## d 分支 新增删除修改记忆

### 复现步骤

1. 输入“记住：我的食物偏好是不吃香菜，测试记忆编号 CodexD0807”。
2. 系统询问是否确认。
3. 回复“对”。
4. 断线重连后查询该偏好。

### 日志证据

- 1.7B 路由到 `d/memory_write`，置信度 0.955，耗时约 60 ms。
- 9B 选择 `memory_write`，耗时约 872 ms。
- 关键词抽取为 `CodexD0807` 和“不吃香菜”，耗时约 529 ms。
- 槽位抽取正确得到 `target=agent_memory`、`content=不吃香菜`，耗时约 1230 ms。
- 回复“对”后再次进入 `memory_write`，置信度降至 0.673，并重复关键词与槽位抽取；没有 memory 主键或提交成功记录。

### 根因

d 与 a 共享同一个确认态缺失问题。确认词没有绑定上一轮的待写入记忆，因此系统重新发起写记忆流程，永远停留在确认前。

### 修复方案

1. 复用统一待确认事务状态机，不为提醒和记忆分别实现临时逻辑。
2. 写入成功后返回 `memory_id`、目标表、版本号和提交状态。
3. 使用幂等键避免重复确认、网络重试和 TTS 重播造成重复记录。
4. 明确画像字段与普通记忆的路由规则，无法确定时先询问，不自动猜测。

### 验收条件

- 确认后一次写入并返回主键。
- 同一幂等键重复提交只保留一条记录。
- 断线重连后可查询到记忆。

## e 分支 查询记忆

### 复现步骤

断线重连后输入“你记得我的食物偏好吗？测试记忆编号 CodexD0807”。

### 日志证据

- 1.7B 路由到 `e/memory_query`，置信度 0.819，耗时约 65 ms。
- 9B 选择 `memory_query`，耗时约 523 ms。
- 关键词抽取只保留 `CodexD0807`，丢失“食物偏好”和“不吃香菜”的语义，耗时约 416 ms。
- 检索候选为空，用户画像为空，系统回复没有保存该偏好，生成耗时约 683 ms。

### 根因

直接空结果主要由 d 未写库造成。除此之外，查询关键词过度依赖显式编号，忽略了用户问题中的语义槽位。即使数据库已有“不吃香菜”，仅用编号检索也可能漏召回。

### 修复方案

1. 先修复 d 并建立跨会话持久化回归测试。
2. 查询词应同时包含实体、属性和值，例如 `食物偏好`、`香菜`、`不吃` 和测试编号。
3. 采用画像字段精确查询、关键词检索和向量召回的混合策略，并对结果去重排序。
4. 空结果时记录每一路召回数量，区分未写入、用户隔离错误和语义召回失败。

### 验收条件

- “我不吃香菜”“我有什么忌口”“点菜时要避开什么”能够召回同一记忆。
- 不带测试编号仍能召回。
- 不同用户之间不得串记忆。

## 共用状态机设计

```text
用户输入
  -> 是否存在未过期 pending_operation
     -> 是：确认 / 取消 / 修改
        -> 确认：执行冻结命令并提交事务
        -> 取消：清空待确认状态
        -> 修改：只更新指定槽位并再次确认
     -> 否：进入 a 至 m 意图路由
  -> 工具执行
     -> status=ok：用业务结果生成成功回复
     -> status!=ok：使用错误码模板并终止
```

待确认对象建议包含：

```json
{
  "operation_id": "uuid",
  "intent": "reminder_create",
  "normalized_payload": {},
  "resolved_at": "ISO-8601",
  "expires_at": "ISO-8601",
  "idempotency_key": "hash",
  "state": "awaiting_confirmation"
}
```

## 日志改造

每轮日志按阶段写入，并以同一个 `trace_id` 串联：

1. `input_received`：脱敏文本、会话 ID 哈希和时间。
2. `router_1`：标签、置信度、是否接受和耗时。
3. `router_2`：工具候选、最终工具和耗时。
4. `slot_extract`：字段是否齐全，不记录敏感原文。
5. `confirmation_state`：operation_id、状态变化和冻结时间。
6. `tool_result`：状态码、业务主键、影响行数和耗时。
7. `response_guard`：允许的事实和禁止的成功断言。
8. `response_sent`：模板或模型版本、TTS 耗时和总耗时。

## 修复优先级

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | 统一确认态和事务提交 | 同时阻断 a、c、d、e，且会造成用户数据丢失 |
| P0 | 工具失败终止和成功话术约束 | b 已出现与数据库相反的成功回复 |
| P1 | 记忆混合召回和跨会话测试 | 避免写入修复后仍查询不到 |
| P1 | 分阶段日志和业务主键观测 | 当前无法从日志证明写库和物化是否成功 |
| P2 | 前端识别 `schedule_sync` 消息 | 当前测试页显示未知消息类型，影响诊断 |

## 最小回归集

1. 新建一次性提醒，确认后立即查询。
2. 同一确认回复重复发送两次，验证幂等。
3. 创建后修改时间，验证旧 schedule 取消、新 schedule 生成。
4. 删除不存在提醒，验证失败话术且无成功断言。
5. 写入食物偏好，断线重连后用三种同义问法查询。
6. 两个用户写入相反偏好，验证数据隔离。
7. 模拟数据库超时，验证 a、b、d 不输出成功。
8. 模拟模型空响应，验证 M4 只重试一次。

8. 失败根因

  1. 9B端点上下文只有8192 token。客户端还设置max_tokens=1024，输入可用预算进一步收紧。
  2. 新版工具面板明显膨胀。13工具Schema从7808字符增至10690字符（+36.9%），UTF-8字节数从11292增至16644（+47.4%）；系统提示从164增至255字符。
  3. 直接复现的HTTP响应：500 Server Error — Context size has been exceeded.。245条失败均发生在低置信M3交接路径，244条只记录到1.7B调用，另1条第一轮9B返回后第二轮失败。
  4. M1吞掉M3异常。except Exception直接返回ok=False，没有保留原M1标签，也没有把HTTP错误类型写入逐条结果，最终表现为无分支路由。
判断：intent_evidence方向本身尚未得到充分验收。多数请求在工具选择或证据校验完成前就失败，不能用“引错从87降到15”证明语义纠错变好。

9. 推荐整改方案

  1. P0：拆成两阶段。第一阶段只让9B输出“最终分支＋逐字依据”，使用轻量枚举或13个空Schema工具；确定分支后，第二阶段只加载该分支表单Schema。
  2. P0：增加token预检。调用9B前通过tokenize计算模板后的完整输入，预留输出预算；超限时裁剪历史或切换轻量面板。
  3. P0：异常必须回退。M3超时、HTTP 500、上下文溢出时保留M1标签，并记录m3_context_overflow或m3_http_error，不能返回无最终分支。
  4. P1：缩短M3输入。证据只允许引用真实用户轮；优先保留当前用户句和解决指代所需的最少历史，不携带无关助手文本。
  5. 重新验收：同一1300条中路由失败必须为0，最终准确率高于90.15%，M3纠正数大于引错数，旧错修复数大于新增回归数。

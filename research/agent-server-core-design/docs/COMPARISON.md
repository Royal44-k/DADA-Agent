# 三套架构：核心机制与业务处理对照

下表是对本专题三份源码分析报告的归纳，不是上游当前版本的重新测评。详细证据、实现路径、风险和版本边界见各报告。

## 核心差异

| 观察维度 | Grok Build | DeepSeek Harness | Pi Agent |
| --- | --- | --- | --- |
| 主要组织方式 | SessionActor、ChatState、Sampler 等明确拥有各层状态 | Cordis 插件树承载能力、依赖与生命周期 | 库内核保持精简，Coding Agent 产品层补会话与恢复 |
| 一次交互的中心 | SessionActor 编排会话、输入队列、模型与工具循环 | 插件化会话循环，日志与能力服务相互组合 | AgentSession → Agent → runAgentLoop → provider |
| 模型上下文 | ChatState 管理历史和请求组装 | 追加日志作为模型可见表面的基础，强调请求重建 | 持久历史与 provider 请求视图区分，在边界修复历史 |
| 工具执行 | 预检、参数规范化、hooks、权限判断，再进入调度 | 工具能力组合、guard、受控并行和有序结果 | 有序 preflight、可并发执行、稳定 transcript；错误结构化 |
| 长期运行 | 会话与连接解耦；重试、回放、压缩、持久化协同 | 插件生命周期、持久化 flush/repair 和日志一致性 | 自动压缩与重试在产品层，会话树支持回退/分叉 |
| 扩展方式 | 工具、MCP 动态发现、hooks 等多个扩展面 | “一切皆插件”，挂载/卸载具有生命周期语义 | 扩展 hooks 覆盖输入、上下文、工具、会话和 UI |
| 安全关键点 | 工具预检和权限边界控制副作用 | capability seam、guard 与作用域约束 | 项目信任不等于沙箱；运行隔离依赖外部边界 |
| 主要工程代价 | 状态与策略复杂，调度中心认知负担高 | 插件依赖、清理和组合顺序需要严格契约 | 简洁内核把较多产品策略留给上层；新旧生命周期路径并存 |

## 典型业务流程

### Grok：可连续运行的执行会话

用户输入 → 会话排队/启动 → ChatState 更新历史与上下文 → Sampler 流式采样 → ToolBridge 预检和授权 → 工具执行/结果回填 → 下一轮模型调用或回合结束。

连接层与执行会话解耦，使客户端断线不必等同于任务结束；请求重试、对话配对修复、压缩与持久化分别处理不同层的故障。其突出价值在于**明确状态所有权和恢复责任**，而不是单纯增加重试次数。

详见 [Grok 完整报告](../reports/grok-core-design-analysis.html)。

### DeepSeek：由插件生命周期支撑的会话执行

加载配置和插件树 → 组合会话所需能力 → 准备模型可见日志与请求 → 模型输出工具调用 → 参数/权限 guard → 执行并写回结果 → flush/修复与后续循环。

插件不仅是静态工具注册表，也承载资源生存期、依赖和撤销。日志与请求可重建性把“模型实际看到了什么”变成可追溯对象；业务功能因此可以围绕清晰能力接口组合，而不是直接侵入主循环。

详见 [DeepSeek 完整报告](../reports/deepseek-harness-core-design-analysis.html)。

### Pi：精简循环外包裹完整产品会话

AgentSession 接收输入 → Agent 运行循环 → 请求边界转换/修复 → provider 流式响应 → assistant 定稿屏障 → 工具 preflight 与执行 → toolResult 反馈 → 继续循环/事件结算 → 产品层持久化、重试或压缩。

JSONL 的 `id/parentId` 形成会话树，当前路径可以变化而无需删除历史。错误尽量变成消息或事件，为模型自修复和上层恢复提供统一反馈。报告同时区分当前产品路径与 Pi 2.0 `AgentHarness` 的迁移方向。

详见 [Pi 完整报告](../reports/pi-agent-core-design-analysis.html)。

## 对 DADA-Agent 的可复用启示（分析建议，尚未实施）

1. **先明确会话状态归属。** 输入队列、当前回合、历史、工具副作用和持久化不能各自维护互相矛盾的状态。
2. **分离模型视图与历史事实。** 请求边界做协议合法化，同时保留可审计历史，不把补救结果伪装成原始事实。
3. **把工具处理拆成阶段。** 参数校验、授权、执行、结果回填和持久化应有独立失败语义；工具失败不等于业务成功。
4. **为恢复定义层级和预算。** 网络重试、解析修复、上下文压缩与业务重放不是同一种动作，需要避免重复副作用。
5. **扩展需要清理与权限契约。** 能加载插件，不代表能安全撤销或隔离插件；生命周期和能力范围应共同设计。
6. **完成应有可核验的结算条件。** 模型文本输出结束、工具结束、监听器结束和数据落盘是不同事件。

以上是借鉴方向，不是已经完成的 DADA 代码修改或性能结论，也不构成三套框架的综合排名。

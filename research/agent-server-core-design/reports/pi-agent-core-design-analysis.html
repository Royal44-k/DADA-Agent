SECTION 01

Executive Summary

执行摘要

Pi Agent 的设计关键词不是“全栈治理”，而是薄内核、清晰边界、容错漏斗和可塑产品层。低层 Agent 只负责消息—模型—工具循环；当前 Coding Agent 用 AgentSession 组织持久化、扩展、自动重试与压缩；下一代 AgentHarness 则正把这些经验收敛成回合快照、保存点和待写队列。

请求边界修复历史

Pi 不要求每个打断点都把历史维护到完美；在发给 provider 前统一丢弃 error/aborted assistant、补齐孤儿 tool result、规范跨模型签名与 id。

错误被转换成反馈

坏 JSON、参数类型错、工具不存在、执行异常和 provider 失败尽可能进入结构化 toolResult 或 assistant error message，让模型和上层策略继续处理。

会话天然可以分叉

JSONL entry 用 id/parentId 形成树。回退到历史点不是删除未来，而是把 leaf 移到旧节点后追加另一条路径；分支摘要可携带被放弃路径的上下文。

总体判断：Pi 更像一套“小而锋利的 Agent 工具箱＋可改造终端产品”。它用少量稳定概念覆盖多供应商、本地开发、四种运行模式和强扩展系统；代价是权限隔离、强一致性持久化与企业级编排主要交给宿主和外部基础设施。

当前产品路径

AgentSession → Agent → runAgentLoop → pi-ai provider。自动重试、自动压缩、SessionManager 与扩展 Runner 位于 Coding Agent 产品层。

演进中的 Harness

AgentHarness 已实现不少生命周期能力，但源码文档明确写明 Coding Agent 尚未采用；自动压缩、重试和完整 session facade 仍在迁移计划中。

SECTION 04

Runtime Loop

Agent 循环：小状态机与清晰事件屏障

runAgentLoop 的主要任务是维护 Context、流式 assistant、工具结果和两类消息队列。低层没有持久化、自动重试或压缩策略，这些由上层根据 agent_end 后的结果继续编排。

01 / Start追加 pending message

发 agent_start、turn_start、message_start/end。

02 / Context边界转换

transformContext 后 convertToLlm，模型只看可理解消息。

03 / Stream部分消息入状态

start 插入 partial assistant，delta 原位替换，结束后定稿。

04 / Toolspreflight + execute

校验、hook、并发执行；结果消息按源顺序产生。

05 / Turnturn_end

prepareNextTurn 可刷新 context/model/thinking。

06 / Queuesteer 优先

有 steering 就继续内层；否则完成当前工作。

07 / Follow-up延后新任务

主循环本可停止时再取 follow-up；最终 agent_end。

两个关键屏障

Assistant 定稿先于工具预检

Agent 会等待 assistant message_end 订阅者完成，再开始工具 preflight。扩展因此能修改或持久化最终 assistant，权限 hook 也能看到已含工具调用的完整 Agent state。

监听器属于运行结算

Agent.subscribe() 监听器按注册顺序 await；即使 agent_end 已发，prompt() 和 waitForIdle() 也要等 agent_end 监听器完成才结算。

Steer、Follow-up 与 Next-turn

  • Steer：当前 assistant 的工具调用执行完后投递，可一条一条或全部交付。
  • Follow-up：当前工作和所有 steer 都结束后才作为新用户消息触发。
  • Next-turn：Coding Agent 的额外产品队列；在下一次用户主动 prompt 时作为上下文一起注入。

shouldStopAfterTurn 是优雅停止点：在完整 turn 和工具收束后、拉取新队列前停止，不篡改 stopReason，也不取消已经运行的工具。

SECTION 05

Tool Reliability Funnel

工具调用：七层容错漏斗

Pi 的工具健壮性不是由一个“重试”开关提供，而是从 JSON 流、参数校验、执行、历史修复到 provider 错误逐层消化。越早修复，越少浪费模型往返；无法修复时则把问题转成对模型可见的错误结果。

流式 JSON 抢救

标准 parse → 修复控制字符/非法转义 → partial-json → 修复后 partial-json → 空对象；流式 UI 始终拿到对象。

Length 安全阀

assistant 因 token 上限截断时，整批 toolCall 拒绝执行，即使残缺参数已被“成功”解析；要求模型重新发完整调用。

串行 Preflight

查工具、prepareArguments、TypeBox/JSON Schema 类型转换与校验、beforeToolCall 按模型顺序执行。

并发执行

默认并行；任何调用指向 sequential 工具时整批串行。执行结束事件按完成顺序，toolResult transcript 按源顺序。

工具内防御

同一真实文件的 write/edit 进入 mutation promise queue；输出按 50KB/2000 行截断，完整内容可落临时文件。

请求边界自愈

丢弃 error/aborted assistant；为孤儿 toolCall 补 No result provided；处理跨模型 signature、tool id 与图片能力。

API 失败分流

配额/账单不重试；429/5xx/网络断流指数退避；上下文溢出进入 compaction，不做无意义原样重试。

并行工具的三阶段设计

serial preflight → concurrent tool bodies → source-order transcript commit

这使 UI 能及时显示先完成的工具，同时让下一轮模型历史不依赖磁盘、网络和进程的随机完成顺序。file-mutation-queue 进一步按 realpath 串行化同文件写操作，不同文件仍然并行。

参数宽容与安全边界

校验前执行 TypeBox Value.Convert 和额外 JSON Schema coercion，可把 "5" 转数字、0/1 转布尔，并递归处理对象、数组与 union。工具还可在 prepareArguments 中兼容特定模型怪癖。

需要留意：当前 Coding Agent 扩展的 tool_call hook 可以原位修改已经校验过的 event.input，后续不会重新校验。它给扩展很大自由，也意味着扩展处于可信边界内，参数修改错误可能绕过 schema 保证。

错误信息就是下一轮提示词

工具不存在、校验失败、execute 抛错或 hook 阻断都转换为 isError:true 的 toolResult。校验错误包含字段路径、预期和值的完整副本；edit 工具还针对找不到、多处匹配、空替换、BOM、CRLF 和尾部空白提供行动指导。

SECTION 06

Append-only Session Tree

会话树：不删除过去，移动当前路径

当前 Coding Agent 的 SessionManager 使用 JSONL v3。Header 之后每条 entry 都有短 id、parentId 和 timestamp，天然形成树。当前上下文只取 root 到 leaf 的 active path，再应用 compaction 规则。

userassistanttoolResultcompactioncurrent leaf
branch_summaryalternate userassistant

同一 JSONL 文件内保留多个未来；tree navigation 只决定下一条 entry 的 parent，不重写已经存在的节点。

对话事实

user、assistant、toolResult 作为 message entry；assistant 自带 provider、model、usage 与 stopReason。

运行状态

model_change、thinking_level_change 等 entry 沿当前路径折叠出会话状态；当前 Coding Agent 的 active tools 由产品运行配置管理。

扩展数据

custom只保存扩展状态，不进模型；custom_message则明确投影到上下文，可选择是否显示。

树导航的业务语义

选择历史 user message 时，leaf 移到它的 parent，并把原用户文本送回编辑器，允许修改后形成新分支；选择非用户节点时直接以该节点为 leaf。可选 branch summary 会总结旧 leaf 到共同祖先之间的被放弃路径，并附在新目标位置，使新分支知道先前探索过什么。

当前实现与下一代持久 leaf 的区别

当前SessionManager 的 branch() 只移动内存 leaf；随后追加 entry 才把新 parent 关系写入 JSONL。AgentHarness Session 的设计则要求把 leaf 改变本身写成耐久 leaf entry，以便只导航、不追加消息时也能在重启后恢复游标。

SECTION 07

Compaction & Recovery

压缩、重试与上下文恢复

何时压缩

默认开启，保留 16,384 token 输出预算和约 20,000 token 最近消息。当估算上下文大于 contextWindow - reserveTokens 时阈值压缩；若 provider 明确或隐式表现为 overflow，则走恢复压缩。

估算上下文

优先使用最后一条有效 assistant usage；之后新增消息按字符/图片估算。error、aborted 和全零 usage 不覆盖最后可靠基准。

选择 cut point

从最新消息向前累积，保留近期预算；可以在 user 或 assistant 处切，但绝不从 toolResult 开始，以维护 tool call/result 结构。

处理超大单 Turn

如果 cut 落在 turn 内，历史摘要与 turn-prefix 摘要分开生成，再合并为一个 checkpoint，保留最近后缀。

增量更新摘要

有前一次 compaction 时，将旧 summary 与新增历史一起交给更新提示，保留 Goal、Constraints、Progress、Decisions、Next Steps。

附加文件操作

从工具调用中提取已读和已修改文件，并将列表写入摘要 details，降低压缩后丢失工作区认知的概率。

重建 Agent 上下文

追加 compaction entry，SessionManager 从 summary + firstKeptEntryId + 后续 entry 重建 active messages。

Overflow 与普通阈值不是同一业务

失败恢复

错误 assistant 保留在 session 作为历史，但从 Agent 工作状态移除；压缩后自动 continue()。一次恢复仍 overflow 就停止，并建议缩减上下文或换大窗口模型。

预防性维护

接近上限但响应成功时只压缩，不重发已完成请求；如果压缩期间有 steer/follow-up 等待，则继续一次以交付队列。

Provider 错误重试

Pi-ai 只提供分类器，上层 AgentSession 执行 baseDelayMs × 2^(attempt-1) 的可中断退避。黑名单先排除 quota、billing、subscription limit；白名单才接受 429、5xx、网络断流、WebSocket 关闭和 provider 明示 retry。上下文 overflow 在分类前被单独拦截。

错误 assistant 从当前 Agent state 移除但仍留在 Session 历史；下一次 provider 请求的 transformMessages 又会跳过 error/aborted assistant，因此“审计保留”与“合法重试上下文”不冲突。

SECTION 08

Extension Runtime

扩展系统：产品可塑性的主要来源

扩展是直接运行的 TypeScript 模块，可注册工具、命令、快捷键、Provider、UI、渲染器和生命周期 hook。Pi 把权限确认、路径保护、Git checkpoint、远程工具路由等都视为扩展用例，而不是固定产品功能。

Input输入拦截

命令优先；input 可 handled 或 transform。

Expand资源展开

skill、prompt template、context files。

Startbefore_agent

注入 message，链式修改 system prompt。

Provider请求观察

context、headers、payload、response headers。

Tools调用门控

tool_call 可改参数/阻断；tool_result 可改结果。

Session结构操作

compact、tree、switch、fork 前后 hook。

Settleagent_settled

确认重试、压缩和队列都不再自动继续。

错误隔离策略

  • 一般扩展事件异常被记录，Agent 继续；一个 extension 不应让其他观察者消失。
  • tool_call handler 异常由 AgentSession 转为阻断，采用 fail-safe。
  • 工具 execute 应通过 throw 表达错误，循环将其转换为模型可见结果。
  • Session before hook 可以 cancel；多个 handler 依次执行，取消立即短路。

工具覆写与远程执行

扩展可以同名覆写 read/write/edit/bash/grep/find/ls；执行与 renderer 按槽位独立继承，但 prompt metadata 不自动继承。内置工具还把文件、shell 等操作抽成 Operations 接口，使 SSH、容器或 Gondolin 后端无需重写模型 schema 和 UI。

信任模型：扩展不是受限插件。它可以 import Node 内建模块、执行任意代码并拥有 Pi 进程的系统权限；只应从可信来源加载。项目 trust 解决“仓库是否可自动注入扩展和配置”，不解决扩展自身的隔离。
SECTION 09

Provider Portability

模型层：统一上下文，适配供应商差异

pi-ai 只收录支持 tool calling 的模型。Provider 是运行单元，拥有模型目录、认证/OAuth 与 stream；不同 Provider 可以共享 Anthropic Messages、OpenAI Responses、OpenAI Completions 等 wire implementation。

Models 集合

按 model.provider 找到 owner，解析动态凭据与 baseUrl，显式 request 选项按字段覆盖认证默认，再交给 provider stream。

错误即消息

流式 API 通过 start/text/thinking/toolcall/done/error 事件表现；最终失败物化为带 stopReason 的 AssistantMessage，便于 UI、Session 与恢复层统一消费。

跨模型切换

上下文可序列化并交给另一模型；请求边界会降级不支持图片、剥离其他模型的加密 reasoning/signature，并规范 tool call id。

跨供应商上下文自愈

transformMessages 做两趟转换：先处理图片能力、thinking block 与工具 id；再扫描历史，跳过 error/aborted assistant，为没有结果的 toolCall 插入合成 error result。修复后的数组只用于请求，原 Session 不被改写。

durable session history ≠ provider request view
request view = transformMessages(active context, target model)

Overflow 检测的生产经验

除了匹配各 Provider 的错误文本，还覆盖“成功但 usage 超窗口”和“输入几乎填满窗口、output=0、stopReason=length”的静默截断模式；rate limit 等含有“too many tokens”的非 overflow 错误先排除，减少误分流。

SECTION 10

Business Processing

产品处理流程与四种运行模式

Pi Coding Agent 在不同宿主中复用同一 AgentSession。差别主要在输入输出 carrier 与 UI 能力，而非模型或工具循环。

“修改代码并验证”的完整业务链

启动与资源发现

解析全局/项目设置、信任决策、AGENTS/CLAUDE context、skills、prompts、themes、extensions 和 provider credentials。

输入预处理

扩展命令优先；input hook 可接管或转换；skill/template 展开；before_agent_start 可注入持久消息和修改本轮 system prompt。

模型与工具循环

Provider 流式返回文本和 toolCall；read/edit/write/bash 等经容错漏斗执行，进度即时显示，结果按调用顺序进入 context。

中途用户控制

Enter 投递 steer，Alt+Enter 投递 follow-up，Escape abort 并把队列恢复到编辑器；模式可配置 one-at-a-time 或 all。

运行后恢复策略

AgentSession 检查 retryable error、overflow 和 threshold compaction；必要时自动 continue，最后才发 agent_settled。

持久化与复用

message_end 追加 Session entry；用户可 tree 回溯、fork/clone、export HTML/JSONL、resume 或通过 RPC 查询 session tree。

终端体验也是核心业务能力

Pi-TUI 通过差分渲染与 CSI 2026 synchronized output 降低流式闪烁；组件 render 返回严格宽度内的行。Overlay 有显式 focus/fallback 语义，编辑器通过硬件光标 marker 支持中日韩 IME 候选框定位。这些不是 Agent 推理机制，却直接决定长时编码会话是否可用。

实验性 Orchestrator

pi-orchestrator 提供 supervisor、RPC process、IPC server 与 storage，但 README 明确标注 Experimental、API 可能变化或删除。它说明 Pi 正探索多进程编排，却不应被视为当前稳定核心能力。

SECTION 11

Security Boundary

安全模型：信任加载，不假装隔离

Pi 明确声明自己以启动用户的权限运行。内置工具、扩展、包安装、shell 和语言服务器都是普通本地进程。项目 Trust 是资源加载守门，不是工具行为沙箱。

防止仓库静默注入

检测项目 .pi 设置、扩展、skills、prompts、themes 与 system files；默认 ask。非交互模式不会弹窗，可由保存决策或 CLI override 控制。

不限制运行权限

信任项目后，模型仍可要求工具执行用户本可执行的操作。AGENTS.md/CLAUDE.md 还可独立加载；Prompt injection 属于本地 Agent 预期风险。

隔离策略必须来自 OS 或虚拟化边界

方案隔离对象注意事项
Gondolin extension内置工具与 ! 命令进入本地 micro-VM其他自定义扩展工具仍可能在宿主执行；workspace mount 可回写宿主
Plain Docker整个 Pi 进程Provider key 进入容器；读写 bind mount 仍修改主机
OpenShell策略控制的本地/远程 sandbox可控制文件、进程、网络、凭据与 inference；远程模式需传输项目文件

安全上的坦诚取舍

项目文档认为“半套 in-process sandbox”容易制造错误安全感，因为工具最终仍依赖 host shell、filesystem、package manager、credential 和 extension code。因此核心选择不提供一个名义权限系统，而是要求高风险或无人监督任务在真正的系统边界中运行。

业务建议：如果把 Pi 用作服务器 Agent 或自动化 worker，必须在产品壳补上明确的工作区挂载、网络策略、短期凭据、扩展 allowlist 和结果审阅；不能直接把本地交互默认值搬到多租户环境。
SECTION 12

Pi 2.0 Direction

AgentHarness：从产品经验提炼生命周期

演进中AgentHarness 位于 agent-core 之上，目标是拥有 session persistence、runtime config、resource resolution、operation locking 与扩展 mutation 语义。文档明确说明 Coding Agent 仍由 AgentSession 驱动，迁移属于 Pi 2.0。

核心新概念：Turn Snapshot

Harness config 是应用最新设置；每次 createTurnState() 再把 session messages、resources、system prompt、model、thinking、tools、stream options 和 session id 固化为本轮快照。Setter 可以在运行中更新未来配置，但不会突变当前 provider request。

live harness config --createTurnState()→ immutable-ish turn snapshot --provider request→ save point

Save Point 与 Pending Writes

消息先提交

Agent 发出的 assistant 与 tool result 在 message_end 按 transcript 顺序持久化。

运行中外部写排队

扩展或应用在 operation 活动期间请求的 session entry 进入 pending writes，不插到当前工具结果中间。

回合保存点排空

assistant turn 和工具结果完成后，先 flush pending writes，再为可能继续的下一 LLM turn 重建 snapshot。

失败也不丢写

pending writes 在 save point、agent_end 或 failure cleanup 排空；abort 清 steer/follow-up，但保留 nextTurn 与 pending writes。

显式阶段与结构操作

Phase 为 idle | turn | compaction | branch_summary | retry。prompt、skill、template、compact、navigateTree 是结构操作，只能从 idle 启动并在首个 await 前占有 phase；steer、followUp、nextTurn、abort 与 runtime setter 则在文档允许的运行边界使用。

尚未完成或仍需审计

  • Auto-compaction 与 retry decision points 尚未进入 AgentHarness。
  • 完整 HarnessSession facade 尚未实现；原始 harness 在部分 hook 中调用 settlement API 仍可能形成重入死锁。
  • phase/settled、abort barrier 与广泛 listener/hook reentrancy 需要进一步生命周期验证。
  • Coding Agent 的资源、扩展、UI/session 行为和 auth/retry/header 流程尚待迁移。
架构判断：AgentHarness 正把 AgentSession 中分散的“下一 turn 刷新、持久化顺序、失败清理”升级成统一保存点协议。方向合理，但报告必须把它视为迁移目标，而不是当前产品已经完成的替代层。
SECTION 13

Review & Reuse

突出设计、风险与可复用原则

最突出的设计点

修复在边界集中发生

持久历史保持真实，provider request view 负责合法化，避免到处维护“永远完美”的中间状态。

并行与顺序分层

preflight 有序、body 并发、事件实时、transcript 稳定；同文件写再加细粒度 mutex。

会话树是产品能力

分叉、回退、摘要、导出都建立在 parentId 上，不需要复制或破坏原对话。

扩展面覆盖整条业务链

输入、上下文、provider、工具、Session、UI 都可扩展，使最小默认值仍能适配个人工作流。

错误尽量数据化

工具异常、provider 失败、overflow 都进入消息或事件，让 UI、历史和恢复策略共享一种观察面。

安全边界诚实

明确说无内置 sandbox，并给出 VM/container/policy sandbox 路径，避免把 project trust 误解为权限隔离。

局限与风险

  1. 默认权限过强，不适合直接服务器化

    本地产品假设用户监督和同一 OS 权限边界；多租户、无人值守或不可信仓库必须补外部隔离与授权。

  2. 当前 SessionManager 的耐久性弱于事件日志系统

    同步 appendFile、无 per-entry checksum/事务；无 assistant 的会话可能不创建文件；仅移动 leaf 不立刻持久化。

  3. 扩展是强信任代码

    可改已校验工具参数且不重新校验，可注册 Provider/工具并执行 Node 代码；扩展供应链等价于本地代码供应链。

  4. AgentSession 与 AgentHarness 双轨期

    当前产品逻辑与新 Harness 重叠，迁移期间容易把文档中的目标行为和实际产品行为混淆。

  5. 错误分类依赖 Provider 文本经验

    retry/overflow 正则覆盖广但不是结构化协议；新供应商、代理网关和本地模型可能返回未识别或误导性文案。

  6. 并行工具的中断历史由请求边界兜底

    串行模式 abort 后未启动调用不会立刻拥有结果；上下文自愈虽可补齐 provider 结构，但 Session 原始路径仍需 UI 正确解释。

可复用原则

原则解决的问题推荐实现
请求边界自愈打断、崩溃、跨模型导致历史非法保留原历史；发请求前统一过滤、降级和补配对
抢救解析必须配安全阀残缺 JSON 被修成“合法但危险”参数stopReason=length 时拒绝全部副作用调用
错误文案就是模型反馈工具失败消耗多轮猜测字段路径 + 预期 + 实际值 + 下一步行动
同资源串行、异资源并行工具并发写冲突以 canonical resource key 建 promise queue/mutex
错误历史与工作状态分离既要审计又要合法重试错误保留 session，从 active context 移除
回合边界快照运行中配置变化污染当前请求live config → turn snapshot → save point refresh

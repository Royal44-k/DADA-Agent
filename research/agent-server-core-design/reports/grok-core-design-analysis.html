01 · Executive summary

它的核心产品不是聊天界面，
而是“可连续运行的执行会话”。

Grok Build 表面是终端编码 Agent，内部却更接近一个单进程、多 Actor 的任务执行平台：连接可以更换，会话持续存在；模型可以失败，回合仍可恢复；工具可以动态出现，但模型看到的接口尽量保持稳定。

核心设计判断：以 Actor 明确状态所有权，以工具调用—结果配对维护对话协议完整性，再用重试、回放、压缩和持久化构成恢复轨。三者共同把概率性模型嵌入确定性业务外壳。 架构推断 基于 SessionActor、ChatState Actor、Sampler Actor、ToolBridge、Persistence 与 WebSocket/ACP 连接实现的交叉分析。

STATE OWNERSHIP

状态所有权优先

会话调度、对话历史、采样传输和持久化分别由明确 Actor 或对象拥有，关键路径以消息传递串行化，降低“大锁 + 隐式共享状态”的复杂度。

PROTOCOL INTEGRITY

工具结果必须闭环

每个工具调用最终都获得对应结果，包括被兄弟调用的权限拒绝连带取消的情况。它把工具批次当作对话协议事务，而非一组随意的异步函数。

CONTINUITY

连接不等于会话

远程 Agent Server 将持久 Agent 线程与可替换 WebSocket/ACP relay 分离。客户端断开时，Session Actor 和运行中的 Prompt 可以继续生存并在重连后恢复输出。

04 · End-to-end flows

一次 Prompt 如何穿过整个系统。

主流程具有两个明显特征：其一，所有对话变更最终回到 ChatState；其二，任何外部副作用都必须经过工具预检与权限边界。模型流和工具流在 SessionActor 中循环，直到产生无工具调用的最终回答或触发停止条件。

Client → MvpAgent
接收 Prompt。 获取会话 intake lock，确定 prompt mode、prompt id、turn number 和排队策略。
MvpAgent → SessionActor
注入输入。 若已有运行任务则进入 FIFO；否则创建本轮任务。取消、send-now 与 verbatim 等模式在此区分。
SessionActor → ChatState
更新对话真相源。 合并用户内容、提醒、记忆与 MCP 变化，检查对话完整性并评估压缩。
ChatState → Sampler
构造精确请求。 依据实际序列化体积治理图片和历史工具结果，再交给对应模型后端的流式采样器。
Sampler → SessionActor
流式回传。 文本、思考、用量和工具调用逐段解析；drain barrier 保证文本事件编号先于工具事件。
SessionActor → ToolBridge
工具预检。 规范化参数、查找工具、执行 hooks、计划模式检查、权限判断；批准后并发调度。
ToolBridge → Workspace
产生副作用。 文件、Shell、搜索、MCP 等返回类型化 ToolOutput；必要时使用路径锁、鉴权刷新或取消令牌。
Result → ChatState
闭合协议。 每个 tool_call 写入配对 tool_result，持久化并再次采样，直到最终答复、预算耗尽、用户取消或 Goal 状态变化。

七类核心业务流程

服务启动与连接恢复

  1. WebSocket /ws 校验 Bearer 或 server-key。
  2. 首次连接惰性创建持久 Agent OS 线程与 Tokio LocalSet。
  3. 当前 ACP 连接替换 relay 目的地；Agent 和 Session 不随 socket 销毁。
  4. 重连后补发缓冲通知并继续在途 Prompt。
INVARIANT · Connection lifetime is shorter than session lifetime.

新建、加载与恢复会话

  1. initialize 建立能力、模型、权限与子 Agent 协调器。
  2. new_session 合并 managed/client MCP，建立持久化目录。
  3. load_session 等待旧线程排空并重新水化对话与模型。
  4. 若原模型不可用则执行模型恢复与元数据修正。
INVARIANT · Persisted session is the recovery contract, not the socket.

Prompt 排队与回合调度

  1. 一个主运行任务对应当前回合。
  2. 普通输入进入 pending_inputs FIFO。
  3. 用户 interjection 可在安全点被吸收；等待型工具可被打断。
  4. turn complete 后排空通知、启动下一输入并发布 idle。
INVARIANT · Synthetic turns cannot sweep away a queued user prompt.

工具批次处理

  1. 先解析和审批全部调用，再开始执行批准项。
  2. 无关工具并发；同一路径读写受文件锁约束。
  3. 任何拒绝或取消都会为后续兄弟调用生成因果结果。
  4. 结果按调用身份回填，不以完成顺序破坏协议。
INVARIANT · Every tool call must have exactly one model-visible result.

MCP 动态工具发现

  1. Blocking 模式等待初始化；Progressive 模式不阻塞首轮。
  2. 隐藏的大工具集通过 search_tool 做 BM25 检索。
  3. use_tool 作为稳定 meta-tool 分派完整限定名。
  4. 工具变化以指纹和 delta reminder 告知模型。
INVARIANT · Dynamic capability should not churn the prompt prefix every turn.

上下文、图片与记忆治理

  1. 按真实序列化请求体而非粗略 token 估算硬限制。
  2. 图片接近 50 MB 才批量降到 25 MB，形成滞回。
  3. 上下文过半时分层裁剪旧工具结果。
  4. 空闲和会话结束时刷新长期记忆并在后续回合再注入。
INVARIANT · Preserve cache-friendly prefixes until a real threshold is crossed.

Goal 自主执行与验证

  1. Goal 在 Planning / Executing 阶段间流转，并可因用户、基础设施或停滞暂停。
  2. 验证阶段并行启动默认 3 个 adversarial skeptics。
  3. 高置信反驳可成为决定性闸门；其余按独立冷评审多数规则聚合。
  4. 可修复缺口回到执行；矛盾或不可验证阻塞则暂停等待用户。
INVARIANT · The model that did the work is not the sole judge of completion.

05 · Core mechanisms

核心机制拆解

以下机制共同决定系统为什么能够长时间运行，而不只是完成一次调用。

M-01
ACTOR SCHEDULER

SessionActor 是业务编排中心

它持有运行任务、待处理输入、通知抑制、回退状态、计划/目标、工具上下文和 MCP 状态等。run_session 使用带优先级的 tokio::select! 同时监听命令、回合完成、ChatState 事件、MCP 重启、内存刷新和模型切换。

  • “是否空闲”由共享判定函数统一定义，避免多个子系统出现不同口径。
  • 单线程 LocalSet 让 Session 内的 Agent 可通过 RefCell 安全访问。
  • 回合结束是业务收敛点：刷新流缓冲、处理 Goal、排空通知、启动下一输入、触发 laziness 检查。
SOURCE · xai-grok-shell/src/session/acp_session.rs · acp_session_impl/run_loop.rs
M-02
CHAT STATE

对话历史不是共享 Vec，而是独立 Actor

ChatState 独占 Conversation、采样配置、token、prompt index、时间信息、编辑路径和持久化接口。写操作以消息串行化，查询使用 oneshot；持久化对象只在 Actor 内以 &mut self 使用。

  • 请求前执行 conversation integrity 修复，处理悬空工具调用和重复记录。
  • 支持 snapshot、fork 和 rewind，为会话分支与文件回退提供一致起点。
  • 图片淘汰只发生在请求副本，原对话仍保留事实；模型看到诚实占位符，明确要求用户重新分享。
SOURCE · xai-chat-state/src/actor.rs · xai-chat-state/src/persistence.rs
M-03
SAMPLER

把模型传输失败隔离在请求任务里

Sampler Actor 为每次请求创建独立任务，适配 Chat Completions、Responses 与 Messages 等后端流，并把普通网络重试、空响应重试和 doom-loop 重试分成不同预算。

  • 连接重置疑似 413 时可移除图片后重试。
  • content-filtered empty 被视为合法，而普通空响应会进入重试。
  • 取消使用 cooperative token；单个 chunk 默认有 300 秒 idle timeout。
  • 5 秒 stream-drain barrier 确保此前文本/思考 chunk 获得事件 ID 后再发布工具调用。
SOURCE · xai-grok-sampler/src/actor/request_task.rs · session/acp_session_impl/turn.rs
M-04
TOOL BRIDGE

类型化工具内核 + 模型友好协议外壳

AgentBuilder 生成 AgentDefinition、系统提示、工具策略和 ToolBridge。Registry 在注册阶段校验 schema、依赖与行为版本，执行时将 JSON 参数解析为类型化调用，再把 ToolOutput 转成模型可读结果和 ACP 更新。

  • 动态工具集合用读写锁保护，但 read guard 不跨 await。
  • 终端取消能力与普通 Registry 分离，避免 kill 命令被正在执行的锁阻塞。
  • call_raw 供 use_tool 内部分派，避免 post-processing 和持久化执行两次。
SOURCE · xai-grok-agent/src/agent.rs · xai-grok-tools/src/bridge.rs · registry.rs
M-05
MCP DISCOVERY

用稳定 meta-tool 承载不断变化的能力

Progressive MCP 不强迫首轮等待所有外部 server。真正的大型动态工具集保持隐藏，模型先用 search_tool 搜索，再以 use_tool(server__tool) 分派。

  • 模型可见工具列表更稳定，有利于前缀/KV cache。
  • 服务器工具使用稳定 FNV-1a 指纹检测变化，只发送 delta reminder。
  • 具备 liveness watcher、可选自动重启、managed token refresh、reauth cooldown 和工具注销。
  • 子 Agent 可以共享父级 MCP client，避免重复握手。
SOURCE · xai-grok-shell/src/session/acp_session_impl/mcp.rs · xai-grok-tools search_tool/use_tool
M-06
GOAL HARNESS

让“完成”成为独立验证结论

GoalTracker 保存阶段、暂停原因、预算、历史和 verifier scratch。Planner 负责形成计划，Strategist 在重复未达成时提供结构性调整，Verifier 则以多个只读 skeptic 子 Agent 审核证据。

  • 默认 3 个 skeptic，数量可配置为 1–5；skeptic 0 是可恢复的 reject gatekeeper。
  • 多评审时 skeptic 0 的“通过票”不用于凑通过多数，但其高置信反驳可以决定性阻断。
  • 所有反驳均属 contradiction/unverifiable 时进入 Blocked；存在模型可修复项则继续 NotAchieved。
  • 单个 skeptic 的异常通常保守退化为 refute；更外围的特定 harness 基础设施失败保留 FailOpenAchieved 通道，避免平台故障永久扣住用户。
SOURCE · session/goal_tracker.rs · goal_classifier.rs · goal_planner.rs · goal_strategist.rs

连接连续性的关键切分

短生命周期：Connection

WebSocket 和每次 AgentSideConnection 可以断开、重建。15 秒 keepalive 负责发现连接状态，relay 目的地随最新连接替换。

长生命周期：Agent + Session

MvpAgent 在专用 OS 线程中只创建一次；SessionActor、ChatState 和运行任务继续存在。断连只是“没有当前通知接收者”，不是会话结束。

架构意义：这是 Server 形态最突出的差异化处理。很多 Agent 把连接、会话和回合绑定在同一 async task 上，一旦 transport 结束就级联取消；Grok Build 明确拆开三者，但相应地必须承担事件重放、陈旧连接替换和会话清理复杂度。

07 · Resilience system

容错不是一个 retry，
而是四层语义恢复。

系统将“协议不可解析”“能力不存在”“执行失败”和“模型行为异常”分别处理。重要设计原则是：可恢复错误进入对话，平台内部错误进入重试或降级，二者不混成单一错误计数器。

L1

参数 / 协议异常

空参数标准化、拼接 JSON 恢复、保留原始参数、wire sanitization。

→ 给模型可修复上下文
L2

工具发现异常

not_found、Progressive MCP 尚未 ready、未限定工具名、native tool 被误用。

→ 指向正确调用路径
L3

执行 / 鉴权异常

类型化逻辑失败、Rust Err、401 刷新、managed MCP reauth、兄弟调用取消。

→ 始终闭合 tool_result
L4

模型行为异常

doom-loop、空响应、懒惰声明、最大回合、结构化输出失败。

→ 专项检测与独立预算

关键恢复案例

异常处理为什么有效
工具参数为空归一化为可解析空对象，再进入类型化解析吸收供应商或模型的轻微 wire 差异
多个 JSON 对象被拼接选择首个最佳匹配且可解析对象，执行一次，并提醒其余对象应拆成独立调用恢复最有价值动作，同时避免静默双执行
参数无法解析生成带原始参数的 tool_result，不让 stream parser 崩溃模型拥有纠错证据，协议仍完整
原生工具被塞进 use_tool明确提示直接调用原生工具，阻断重复错误路径针对性错误文案比通用 not_found 更容易恢复
工具批次中途拒绝后续每个 sibling call 获得“因前序拒绝未执行”的结果避免 dangling tool calls 污染下一次模型请求
并发调用同时 401共享 OnceCell 合并 token refresh；managed MCP reauth 后只重试一次避免刷新风暴与重复副作用
模型思考尾部重复仅对高置信 tail repetition 丢弃该次 poisoned attempt，使用独立预算和短 jitter 重试不把普通工具错误误判为模型循环
模型声称完成但缺少行动空闲后独立 laziness classifier 对比声明和工具证据，再按类别注入提醒判定与主模型解耦，证据来自不可伪造的运行态
错误必须进入正确语义层

工具执行错误不参与 doom-loop 计数；模型行为异常由专门信号判断，避免“错误多 = 模型坏”的粗糙策略。

Wire 表示与模型表示分离

向供应商发送可接受的安全参数，同时在 tool_result 中保留足够原始上下文，让模型知道自己哪里错了。

恢复不能制造重复副作用

401 重试受限、拼接 JSON 只执行一个、use_tool 使用 raw dispatch，均围绕“最多一次业务后处理”设计。

超出预算时可接受而非崩溃

Doom-loop 重试耗尽后接受当前输出；某些检测器解析失败时宽松退出，确保辅助机制不会成为主流程单点。

08 · Permission & security

模型提出动作，系统决定动作能否发生。

安全边界主要位于 WorkspaceOps、权限管理器、工具 preflight 和 hooks。模型的“意图”不能绕过这些确定性或受控决策点。

ASK

显式询问

高风险或无法静态证明安全的操作进入用户授权交互；pending-interaction guard 防止状态失配。

AUTO

自动评估

快速规则、危险模式、项目指令、历史决策与可选 LLM side-query 共同判断；解析失败回到保守 heuristic。

YOLO

总是批准

可由用户启用，但 managed policy 能钉住关闭并移除 catch-all allow，组织策略优先于会话偏好。

09 · Design highlights

最值得关注的十个设计点

连接—会话—回合三层解耦

WebSocket 可以消失，ACP relay 可以替换，Session 和在途 Prompt 仍继续；它把远程 Agent 从“请求处理器”提升为“持续执行实体”。

业务价值：断线恢复与长任务连续性

Actor 化状态所有权

Session、ChatState、Sampler 分别拥有不同层次状态，持久化也由 ChatState 独占接口访问，减少共享锁和跨层写入。

工程价值：可推理的并发边界

工具调用配对不变量

批准、拒绝、取消和执行失败都必须形成 model-visible tool_result；批次中止也显式补齐因果结果。

协议价值：下一轮请求始终完整

先预检全批次，再并发执行

权限交互和计划模式在副作用之前完成；批准项进入 FuturesUnordered，涉及相同文件时再使用细粒度锁。

性能价值：安全约束下的最大并行度

动态 MCP 的稳定接口策略

search_tool + use_tool 避免把所有动态工具 schema 每轮塞入提示词，既控制上下文，也保护 KV cache 前缀。

成本价值：能力规模与提示规模解耦

缓存感知的上下文滞回

图片不到高水位不动，一旦触发则批量降到低水位；避免每轮小幅清理导致系统提示前缀频繁改变。

成本价值：稳定缓存与请求体安全

专用异常信号替代统一错误计数

Doom-loop、空响应、工具失败、401 和懒惰声明拥有不同判定器与预算，避免恢复策略互相污染。

可靠性价值：更少误重试与重试风暴

错误文案本身经过恢复设计

未限定 MCP 名、原生工具误走 use_tool、Progressive MCP 未 ready 等都有直接告诉模型下一步的消息。

模型价值：降低“doom loop”概率

独立评审者验证 Goal

执行模型不能单方面判定成功；多 skeptic、决定性高置信反驳、停滞指纹和阻塞分类形成外部约束。

产品价值：提高自主任务可信度

Local / Proxy Workspace 双模式

文件、VCS、代码导航和执行通过共享 typed RPC 定义既可本地运行，也可转给远程 workspace server。

部署价值：同一 Agent 支持不同宿主边界

10 · Trade-offs & risks

强韧性来自显著的状态与策略复杂度。

这套设计的风险不是缺少机制，而是机制很多。多个恢复层、动态工具、权限、会话持久化和自主 Goal 会形成组合状态空间，需要非常强的事件、测试和可观测性纪律。

SessionActor 可能成为“业务上帝对象”

它同时管理调度、通知、MCP、权限、记忆、Goal、hooks 与工具上下文，虽然状态集中便于一致性，但文件和认知规模很大。

现有缓解：把 ChatState、Sampler、ToolBridge、Persistence 分拆为独立边界，并以子模块组织 turn/tool/mcp 逻辑。

回放与重连要求严格事件语义

当 relay 可替换且通知可缓冲，客户端必须正确处理事件 ID、重复、遗漏和断点；否则“连续性”会转化为 UI 状态错乱。

现有缓解：stream-drain barrier、replay buffer 与 Session 侧通知顺序控制。

动态 MCP 增加运行态不确定性

工具可能未 ready、掉线、重启、改 schema 或鉴权失效。模型的工具认知也可能落后于真实 registry。

现有缓解：变化指纹、delta reminder、search_tool 状态、自动重启与失效工具注销。

恢复策略可能制造隐藏成本

多类重试、laziness 分类器、Goal skeptic panel 与 strategist 都会追加调用和延迟，且配置组合复杂。

现有缓解：独立预算、idle 条件、会话上限、短路判定、最大回合与最大 verifier runs。

Goal 的 fail-open / fail-closed 边界难以解释

单评审异常倾向保守反驳，而更外围的基础设施失败又可能放行，正确但不直观；用户可能难以理解为何某次被阻塞、另一次被接受。

建议关注：在用户层展示判定来源、失败类别、details path 和最终聚合理由。

错误反馈也可能污染模型行为

过长 tool_result、频繁 reminder 或不精确的恢复文案会消耗上下文并诱导新的错误模式。

现有缓解：结果截断、变化 delta、提醒持久化去重、原始错误与模型表示分离。

总体评估

维度评估理由
会话连续性突出连接与执行实体明确解耦，并配套 replay/persistence。
工具协议完整性突出全批次预检、调用结果配对、类型化输出和因果取消。
扩展性较强Tool Registry、MCP、Hooks、Skills、Plugins 与 Workspace Proxy。
安全边界较强多层权限、命令解析、managed policy 与凭证隔离。
实现复杂度很高Session 编排、恢复机制与动态能力存在大量组合状态。
可验证性依赖测试架构提供 trait、mock 与事件，但正确性高度依赖状态机和回归用例。

11 · Reusable principles

可复用的 Agent Server 架构原则

值得直接借鉴

  • 将 connection、session、turn 建模为不同生命周期。
  • 让对话状态和持久化拥有唯一写入者。
  • 把 tool_call / tool_result 配对设为硬不变量。
  • 先完成整批 preflight，再并发执行批准项。
  • 为不同失败建立不同预算与恢复策略。
  • 动态能力通过稳定 meta-interface 暴露。

需要结合场景取舍

  • Actor 模型是否适合团队的调试和观测能力。
  • 是否真的需要断线后继续运行在途 Prompt。
  • MCP 工具规模是否足以抵消两阶段发现成本。
  • 自主 Goal 是否值得多模型验证的成本与延迟。
  • fail-open 与 fail-closed 应按故障层级明确，而非全局统一。
  • 权限 LLM classifier 只能作为受控补充，不能替代确定性边界。

结论

Grok Build 的优秀之处，不在于某个孤立算法，而在于它把概率性模型包裹进一套具有状态所有权、协议完整性、主机权限与恢复预算的确定性运行时。它最像“Agent 操作系统”的地方，是能够持续接收输入、保存过程、执行副作用、面对断线和错误，再把系统重新带回一个可继续对话的合法状态。

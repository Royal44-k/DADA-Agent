01

执行摘要

DeepSeek Harness 的中心思想可以压缩成一句话：用可重建事件日志固定事实，用 Cordis 可逆插件树组织能力，再用作用域与单调策略限制每一次执行。 因而它的“核心”不是某个不可替换的 Agent 类，而是一组稳定契约：事件、服务 seam、作用域、生命周期和日志投影。

事实先于对象

Session 的追加式事件日志是状态真源。模型历史、UI 回放、工具配对、压缩边界与请求上下文都从日志派生，而不是各自维护一份可漂移状态。

组合先于继承

所有组件以 Cordis plugin 贡献服务、事件和 effect。依赖通过 inject 声明，注册行为随 fiber 生命周期可逆卸载，HMR 与配置叠加因此成为结构能力。

策略只能收紧

工具限制求交、guard 只能拒绝、调用方 AbortSignal 不可被 wrapper 绕过、受限沙箱不可静默降级，共同形成“后置扩展不能重新打开权限”的单调性。

总体判断：DeepSeek Harness 更像“Agent 操作系统内核＋插件化发行版”，而不是单体 Coding Agent。其最大价值不只是功能丰富，而是把功能替换、热更新、审计、恢复和多宿主接入放在同一套生命周期语义中。

最突出的工程能力

请求可从日志精确重建；插件卸载可以逆序撤销；工具并发保持模型顺序；中断与崩溃保留成对历史；子代理能力声明和权限过滤在启动前完成。

最需要注意的代价

抽象层与包数量很高，正确性依赖跨包契约；当前仍为开发者预览，格式迁移尚未稳定；Web 非 loopback 暴露、Web Fetch 私网访问和部分沙箱后端都需要部署者主动评估。

三条结构原则

Loop 可替换

core/agent定义公开 Agent 接口与 registry；默认 core/agent-loop只是一个实现。扩展不应反向依赖具体循环。

Capability 有中层

模型面对稳定工具名；工具消费者面对稳定 seam；供应商只负责实现。Web search/fetch、sandbox、subagent 都遵循这一分层。

Profile 是发行版

配置按 base、产品 bundle、用户 profile、home patch、CLI overlay 分层合成；同一核心可装配为 Web、headless 或定制宿主。

分析推断：其竞争优势来自“架构选择成本低”。换模型、换持久化、换搜索提供方、换沙箱或换 Agent Loop 时，业务层仍使用原有的能力词汇和日志语义。
04

Cordis：时空可组合的插件树

Cordis 不只是依赖注入容器。它同时承担服务仓库、插件生命周期树、事件总线和可逆副作用管理，因此一个插件“何时存在、在哪个 scope 有效、卸载时撤销什么”由同一套模型回答。

声明依赖

插件用 inject 指明所需服务。框架等待服务可用，减少手工装载顺序；依赖缺失与上下文不活跃能被明确暴露。

贡献能力

插件向 ctx 注册服务、事件或 registry 项。注册返回 disposer，并被当前 fiber 的 effect 生命周期接管。

作用域生效

全局层与精确 scope overlay 叠加。Agent 作为不透明 ScopeKey；子 Agent 获得平坦的新 scope，而不是把父级权限隐式继承进去。

事件编排

emit同步观察、waterfall中间件短路、parallel并行等待、serial有序等待。不同一致性需求不用硬塞进一种发布订阅。

逆序卸载

插件停止、HMR 或 scope dispose 时，effects 按所有权撤销到静止状态，防止工具、路由、监听器和临时服务泄漏到下一个实例。

配置层的“整行替换”

Profile patch 不是随意深合并插件内部字段，而是替换或插入一整条配置行。这样能避免“半个旧插件配置＋半个新配置”的组合，同时让 bundle 的装配意图可审计。

effective profile = base → product bundle → named profile patch → home patch → CLI overlay

真实失败揭示的边界

ACP post-mortem 表明，namespace plugin 一旦同时提供默认导出，Loader 会解包到裸 apply 函数并丢失同级 inject；另一个问题则来自 traceable shadow 的祖先式服务查找。修复不仅改代码，还增加真实 Loader/stdio 入口测试，并形成“可选服务使用 ctx.get()”的规则。

关键教训：插件框架的正确性不能只靠手工 mount 单测；至少要有一条测试穿过真实 Loader、export 归一化、fiber 拓扑与运输协议。
05

Agent 运行循环：Turn、Step 与双收件箱

默认 ReactLoopAgent 将一次运行拆成 Turn 与 Step：Turn 表示一次用户驱动的完整工作，Step 表示一次模型请求及其工具结果推进。外部消息根据语义进入“下一回合”或“下一步”收件箱。

01 / Wake领取 next-turn

打开 turn 后再认领输入；即使输入随后被 hook 清空，也保留耐久空 turn。

02 / Pre-step组装请求上下文

收取 next-step、投影历史、应用 context 和 pre-step waterfall。

03 / StreamLLM 流式响应

逐块写 assistant/chunk，结束后组装权威 assistant/message。

04 / Tools有序并发执行

记录 call，执行、提交 result；工具可能要求继续下一 step。

05 / Decide继续或结束

无工具则完成；max-tokens 在 turn 内具有粘性；stopping hook 最后裁决。

06 / Close写入 turn/end

无论完成、阻塞、中断或内部错误，驱动都尽量闭合 turn。

三种投递语义

  • followup：放入 next-turn，并唤醒一个独立回合。
  • steer：投递到最近的 next-step，及时改变当前工作方向。
  • inject：也面向 next-step，但本身不唤醒 Agent。

有因取消

取消原因是 user | parent | hook | disposed，而非无语义布尔值。活动操作采用 first-cause-wins；中断后到达的唤醒消息不会被当前 turn 错领，而是路由到下一 turn。

发布前事务化创建

ctx.agents.create/resume 返回带 dispose 的能力句柄。Agent 在 id 对外发布前先完成 scoped setup；setup 拒绝、commit 失败或 owner 提前销毁都会回滚，不会留下“registry 可见但依赖尚未装好”的半成品。

维护阶段的并发语义

whenIdle 跟随替代工作直到真正静止；runMaintenance 明确拥有 idle maintenance 阶段，后到唤醒会排在维护之后。它解决了常见竞态：界面看到 idle 后开始压缩，但新消息已在同一间隙启动。

06

事件日志：事实层、表面层与请求重建

Session 是单调递增 seq 的追加式类型事件流。模型可见历史不是第二份数据库，而是由各事件声明的 surfaceOp 投影得到：普通消息 append，压缩则 replace 一个表面区间。

原始事实层

turn/start、step/start、每个 assistant chunk、tool/call、tool/result、策略变化和扩展事件都按 seq 保留，用于精确 UI 回放与审计。

模型表面层

模型只看 user/message、组装后的 assistant/message 与 tool/result。Surface node 记录它来自哪些源事件及 append/replace 操作。

请求证据层

request/header 固化 adapter 默认值、最终 system prompt 与工具 schema；request/context记录 provider、model、context window 等路由事实。

model request = logged request/header + surface-derived history + logged route context

为什么同时记录 chunk 与 assembled message

Chunk 是 UI 按原样复现流式体验的事实；assembled assistant message 是模型历史的权威语义。二者角色分开，可以既保留传输细节，又不让半截流事件污染下一次模型请求。

日志写入前的 Lossless JSON 门槛

append 在提交前深拷贝并校验一次：拒绝 BigInt、函数、undefined、NaN、负零、循环引用、稀疏数组和奇异对象。提交后对象被冻结；观察者异常被隔离，不能回滚已经写入的事实。

问题设计处理得到的保证
压缩会改变模型历史在 surface 写 replace，不删除原始事件模型视图更新，审计事实仍在
插件新增未知事件未知 required 事件拒绝格式；仅 ignorable:true 可跳过不会静默丢掉影响语义的事实
Fork 截断不平衡历史只允许在明确、平衡且 turn 关闭的边界 fork新会话不会从半个工具链开始
崩溃留下开放 turn恢复时追加合成 turn/end: interrupted不截断巨型日志，也能闭合生命周期
07

模型与工具：绑定路由、单调门控、有序并发

LLM 请求的 TOCTOU 防护

PreparedLlmCall 把准确模型解析、adapter 默认值、上下文元数据、重试策略与一次性 stream dispatch 绑定到同一 serving registration。这样从“读取模型配置”到“真正发请求”之间即使发生 HMR 或路由替换，也不会把一半旧配置和一半新 adapter 拼成一次请求。

流式协议约束

统一 block-start/delta/end、usage、finish；usage 必须先于 finish，finish 后不得再有数据。中央 BlockAssembler 容忍跨 provider 差异，并在 max-token 截断时丢弃不安全工具调用。

耐久重试

一次 adapter 调用只代表一次 provider 尝试，SDK 内部重试关闭。Agent 级重试会开启一个新的可记录尝试；失败尝试不提交 assistant/tool 副作用。

工具执行管线

Schema显式模型白名单

schemas()只暴露 ToolSchema，不让 timeout、presenter 等宿主元数据泄漏给模型。

Freeze参数定稿

JSON 解码、lossless 校验、深冻结；日志、UI 和执行共享同一参数事实。

Pre策略瀑布

allow/deny/ask决策；作用域 restriction 对继承工具求交。

Guard单调拒绝

guard 只能 deny，不能在后置阶段重新 allow；调用方 signal 被强制融合。

Execute包装器与实现

执行 wrappers、工具 body、post-execute；throw 被标准化为结构化错误。

Commit模型顺序提交

finalizeContent 后生成不可变结果；execution-local value 不必进入耐久日志。

调度器：并发完成，顺序提交

  • 默认滚动并发池上限 10；exclusive 工具形成屏障，前后都不能越过。
  • tools/pre-execute 按模型顺序执行；只让真正的 tool body 重叠。
  • 完成可以乱序，但 tool/result 与上下文接受严格按模型调用顺序提交，保证重放确定。
  • 中断后不再补充新任务，等待已启动任务收束，并为未派发调用写成对的合成 call/result，避免孤儿。
  • 每个 result 引用其 call event seq；内部调度失败会显式暴露不配对条件，而不是伪造成功。
设计亮点：把“执行顺序”和“提交顺序”解耦，使 I/O 并行获得吞吐，同时不把操作系统完成时序写进模型历史。
08

持久化与恢复：异步批写但不模糊顺序

内存日志 append 是同步事实；持久化插件通过 session/event 复制事件并按固定批窗口落盘。追加路径不被磁盘 I/O 阻塞，但 session/flush 是进入下一普通 turn 前的显式顺序与错误检查点。

Append

事件先成为内存事实并广播；后台控制器接收副本。批处理截止时间不因新事件重置，避免持续流量无限拖延。

Batch write

写入期间到达的事件进入下一批。后台写失败时保留待写事件并暂停自动重试；下一事件或显式 flush 触发重试。

Flush to quiescence

取消等待并持续排空直到静止；用于 turn 边界、dispose 和调用方显式持久性要求。

Inspect / Load

inspect构建不可变逻辑视图，不发布 Agent、不写修复；冷加载可修复开放 turn，live load 则等待平衡或拒绝。

Resume / Fork

恢复读取 header 与事件；fork 深拷贝合法 seed。session/end-seed标出外来历史结束，帮助扩展识别 seed 之前的陈旧括号。

JSONL 后端

逻辑上仍是 append log；默认用带校验的拼接 Zstd frame 和原子写策略，实现较紧凑的会话文件与崩溃容忍。

SQLite 后端

每个 SessionEvent 一行，不创建另一套业务 schema。更换存储不改变日志的类型、序号或重放语义。

格式拒绝优于猜测迁移

当前开发预览尚未提供通用迁移器；实现会明确区分更新/过旧格式、损坏数据和未知 required 事件。短期体验较严格，但避免把不理解的状态“尽量加载”后继续执行真实工具。

09

压缩、子代理与目标：围绕 Seam 生长

Compaction：修改表面，不抹除事实

压缩是可选 capability，不嵌进循环核心。操作写入 compaction/start、summary、end，summary 本身是独立 user/message，并通过 surface replace 覆盖旧区间。end最后写，崩溃留下的 orphan start 因而可检测。

  • 自动压缩挂在 serial agent/pre-step，压力与 overflow 使用同一 seam。
  • 可先运行 tool-result pruner；若已降低压力，则不必调用摘要模型。
  • 区域边界维护 tool call/result 配对，但不强制保留整个 turn。
  • request-error 只有在 surface replacement generation 确实推进后才允许 retry。

Subagent：能力协商先于启动

一次性任务

Provider 可能是进程内 spawn/fork、ACP、Codex、Claude Code 或 DSH SDK。Start 前检查输出 schema、深度、persona、tool filter 等能力；不支持就响亮失败。

可继续子代理

Continuation manager 拥有子 Agent 身份、句柄、prompt 投递、冷恢复与 dispose。descriptor 固化 provider/model/persona/filter，避免恢复时改变原任务语义。

父级只提供 cwd、lineage 与 delegationDepth；子级获得新平坦 scope，不继承父级 registry overlay。Tool filter 在 scope registry 层生效，所以被禁工具既不会出现在提示词，也无法从执行入口调用。

Goal：轻量事件溯源的会话目标

Goal 状态为 active、paused、blocked、complete；每次变更携带 id + revision 并使用 CAS，耐久事件保存完整快照或 clear tombstone。它提供同会话的连续目标和轮次上限，但并不是独立、对抗式结果验证器。

Code Runtime / Code Mode

模型可以提交异步程序并调用宿主明确提供的 binding，以减少多次工具往返。运行时把 exception、timeout、abort、worker-exit、invalid-output、output-limit 分开；“worker 隔离”只是实现描述，不被包装成安全承诺。嵌套工具调用仍携带 parent token 和确定性 sub-call id，继续进入日志与策略管线。

10

权限与安全边界：显式、分层、Fail Closed

Approval：没有隐式“默认放行”

结果为 allowed-once | rejected | cancelled | unavailable。策略只有 ask 与 never；never 会在 answerer 之前拒绝，prepend 插件无法绕过。没有回答器、回答器异常或回答器不拥有请求均变成 unavailable，而非继续执行。

Sandbox：文件效果策略按调用解析

模式边界关键语义
read-only拒绝写入，仅允许运行所需 sink具体 backend 报告 full/partial enforcement
workspace-write允许 workspace root 与后端承诺的 temproot 来自 session immutable cwd，并做文件系统语义 canonicalize
danger-full-access绕过 confinement消费者直接执行原 argv，不把危险模式假装成 sandbox provider

受限策略如果没有可用后端，抛出 SANDBOX_UNAVAILABLE；静默无沙箱透传非法。执行结果区分“命令被正常沙箱拒绝”与“沙箱 runner 在命令开始前失败”，避免把基础设施故障误报为业务命令错误。

Permission Preset 只是两个旋钮的视图

Preset 把 sandbox mode 与 approval policy 打包成客户端选项，但自身不执行安全策略。切换时先写 permission/preset 用户意图，再经各自 canonical setter 写旋钮事件；如果当前组合不匹配预设则派生为只读的 custom。

边界声明：Sandbox 的 mode 只描述文件效果，不承诺网络和进程可见性。Windows ACL 与旧 Landlock 可能是 partial enforcement；要求绝对边界的调用方必须拒绝 partial，而不能把“有沙箱”当作二元布尔。

Web 与 GUI 暴露面

  • HTTP host 只允许 127.0.0.1 或 0.0.0.0；后者没有 TLS、认证或 origin policy，属于明确网络暴露。
  • 本地 web fetch 会限制协议、redirect、大小、字符和超时，但当前不阻止私网目标；敏感环境不应随意启用。
  • Client bundle 通过 manifest content hash 与 graph rev 建立一致性；未知插件脚本返回 404，不让 SPA fallback 的 HTML 冒充 JavaScript。
11

业务处理：从用户请求到可恢复结果

以下以“用户要求修改代码并验证”为例，串联宿主、Agent、模型、工具、权限和持久化。DeepSeek Harness 的业务处理不是一个长函数，而是一组在事件边界协作的插件。

1. 宿主接入与会话选择

CLI/Web/ACP 将用户消息映射为 Agent inbox 操作；创建新 Agent 或从持久化 descriptor 恢复。Web 与 Electron 使用不同 carrier，但调用相同 host/client RPC 能力。

2. 回合打开与请求固化

Agent 打开 turn、认领消息、组装 system prompt、工具 schema 与 surface 历史；最终 request/header 和 route context 先进入日志，使“模型看到了什么”可复查。

3. 模型规划与流式反馈

LLM adapter 将供应商流转成统一 block stream；chunk 立即供 UI 观察并写日志，assembled message 成为下一步模型历史。

4. 工具门控与执行

读取、搜索、shell、编辑等调用经 schema、restriction、approval、sandbox policy、guard 和 wrapper；独立工具可并发，exclusive 工具建立屏障。

5. 结果推进

tool result 按模型顺序提交；模型继续解释结果、修正错误或发起下一组调用。Steer 可在最近 step 插入新方向，followup 保留为下一回合。

6. 验证与结束

测试输出和差异同样成为工具结果；无后续工具时进入 stopping seam，最终写 turn/end。错误、blocked、aborted、max-tokens 都有显式 reason。

7. Flush、恢复与继续

持久化排空到静止。崩溃后冷恢复闭合开放 turn；长会话通过 surface compaction 继续；需要并行拆分时由 subagent seam 创建受限子任务。

多客户端与 Web 业务

Web Server 只是 HTTP carrier，不理解 Agent；每条 API、插件 bundle、HMR SSE 都由独立插件注册。路由优先级固定为 exact → 最长 prefix → 唯一 fallback；重复路由在装配期报错。Client Modules 扫描声明 dsh.client 的包，生成注入 window.__DSH_BOOT__ 的插件图；浏览器端按依赖边等待并懒加载。

相关 post-mortem 进一步强化了运行上下文：Agent 必须知道当前 GUI URL 与 production/dev 模式；“构建成功、HTTP 200、boot manifest 存在、用户正在使用的页面已更新”是四个不同验收事实，替代服务器不能证明原页面生效。

12

突出设计、局限与可复用原则

值得突出的设计点

请求级可重建性

不仅保存聊天消息，还保存最终 system prompt、tool schemas、adapter 默认值和路由上下文。线上问题可以从日志回答“那一次模型到底收到了什么”。

生命周期即资源所有权

服务、监听器、工具和路由都归 fiber/effect 所有，scope disposal 到静止。热更新不是额外清理脚本，而是核心资源模型的自然结果。

并发不污染历史

工具 body 并发、模型顺序提交、取消后成对补齐，使吞吐、UI 实时性与重放确定性兼得。

扩展点自带失败语义

waterfall/serial/parallel、unknown required event、sandbox unavailable、approval unavailable 都定义了不能继续时怎样失败，而非让每个插件猜测。

子代理不继承隐式权力

新 scope、能力检查、tool filter、depth 与 descriptor snapshot，把委派从“创建另一个 Agent”提升为有边界的授权协议。

Post-mortem 反哺架构

真实 Loader、服务 shadow、GUI 验收等故障被沉淀为入口测试、文档规则和模型可见运行事实，体现较强的工程学习闭环。

局限与风险

  1. 开发者预览与迁移成本

    版本和事件格式尚可能破坏兼容；当前格式拒绝策略安全但会把迁移责任推给部署与工具链。

  2. 抽象密度高

    大量 package、service seam、Cordis fiber 与事件契约提高了正确扩展的学习成本；局部改动可能触发跨包不变量。

  3. 安全能力不是统一绝对边界

    Sandbox 只覆盖文件效果，且有 partial 后端；Web Fetch 可达私网；Web 非 loopback 没有内建认证。

  4. 可观测事实数量巨大

    chunk、request header、工具、插件事件都进入日志，长期会话需要持续关注存储体积、索引与隐私策略。

  5. 组合灵活性带来组合爆炸

    Profile、HMR、可选 provider 与 scope overlay 的交叉必须依赖 invariants 和真实入口测试，否则单包覆盖率不足以证明整机可用。

可复用的 Core Design 原则

原则适用问题落地方式
模型可见即记录线上请求难复现最终 prompt/schema/route 与历史来源全部耐久化
事实与投影分离压缩、隐藏、重放相互冲突append-only log + replaceable surface
执行并发、提交有序工具吞吐与历史确定性冲突滚动池/屏障 + source-order commit
策略后置只能收紧插件绕过前置授权restriction 取交、deny-only guard、signal 融合
能力协商先于副作用子任务启动后才发现不支持capability check + descriptor snapshot
真实入口是测试对象单测绿但产品不可用真实 Loader/stdio/browser/origin 的无密钥 E2E

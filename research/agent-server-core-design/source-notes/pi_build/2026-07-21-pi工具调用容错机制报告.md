# pi Agent 工具调用与容错机制精读报告

> 精读对象：`pi_build/`（earendil-works/pi，原 badlogic/pi-mono，克隆于 2026-07-21，HEAD = c8c3cd49）
> 精读范围：`packages/ai`（LLM API 层）、`packages/agent`（agent 循环层）、`packages/coding-agent`（会话/工具层）
> 关注点：一次工具调用从模型输出到结果回填的完整链路，以及每个环节的容错设计

---

## 0. 总体架构：工具调用在哪几层之间流动

pi 把工具调用链路切成三个包，职责边界很清楚：

```
┌─────────────────────────────────────────────────────────────┐
│ packages/coding-agent   会话层（AgentSession）              │
│   · 自动重试（指数退避）· 上下文溢出→自动压缩                │
│   · 内置工具实现（bash/edit/read/grep...）                   │
├─────────────────────────────────────────────────────────────┤
│ packages/agent          循环层（agentLoop）                 │
│   · 主循环：LLM流式响应 → 提取toolCall → 执行 → 结果回填     │
│   · 参数准备/校验、并行/串行调度、before/after 钩子          │
├─────────────────────────────────────────────────────────────┤
│ packages/ai             API 层（streamFn + 消息转换）        │
│   · 各家 provider 适配、流式解析、JSON 抢救                  │
│   · 发请求前的上下文自愈（孤儿工具调用补结果）               │
│   · API 错误 → stopReason="error" 的 assistant 消息          │
└─────────────────────────────────────────────────────────────┘
```

一次正常调用的数据流：

```
LLM 流式输出
  → AssistantMessage.content 里出现若干 toolCall block（流式期间用抢救式解析器实时解析参数）
  → 循环层过滤出 toolCalls（agent-loop.ts:202）
  → 逐个 preflight：查找工具 → prepareArguments 归一化 → schema 校验 → beforeToolCall 钩子
  → 执行（默认并行，见第 1 节）
  → 每个 toolCall 产出一条 ToolResultMessage（role: "toolResult"，含 isError 标志）
  → 结果 push 回上下文，进入下一轮 LLM 调用
  → 模型不再发工具调用时，循环结束
```

**贯穿全链路的核心设计哲学：工具层面的任何失败都不抛异常、不打断循环，而是包装成 `isError=true` 的 toolResult 喂回模型，让模型看着错误信息自行纠正重试。** 异常只在两种情况下真正终止循环：API 层错误（stopReason="error"）和用户主动打断（stopReason="aborted"）。

## 1. 多工具调用：支持，且默认并行执行

（回答"pi 是否支持多工具调用"——支持，而且做得比较讲究。）

### 1.1 一条消息多个调用

模型一条 assistant 消息里可以带任意多个 toolCall block。循环层直接从 content 过滤：

```ts
// agent-loop.ts:202
const toolCalls = message.content.filter((c) => c.type === "toolCall");
```

### 1.2 两种执行模式：全局配置 + 每工具覆盖

`packages/agent/src/types.ts:254-263, 396-402`：

- 全局配置 `toolExecution: "sequential" | "parallel"`，**默认 "parallel"**
- 每个工具可以声明 `executionMode` 覆盖全局。**批内只要有一个调用命中 `executionMode: "sequential"` 的工具，整批降级为串行**：

```ts
// agent-loop.ts:417-424
const hasSequentialToolCall = toolCalls.some(
    (tc) => currentContext.tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
);
if (config.toolExecution === "sequential" || hasSequentialToolCall) {
    return executeToolCallsSequential(...);
}
return executeToolCallsParallel(...);
```

官方示例里用 sequential 的场景：操作共享状态、需要向用户逐个提问的工具（`examples/extensions/question.ts`、`tic-tac-toe.ts`——后者注释明说是为了防止兄弟调用在共享游戏状态上竞态）。

### 1.3 并行模式的精细设计（agent-loop.ts:488-553）

并行不是简单 `Promise.all` 一把梭，分了三个阶段：

1. **preflight 永远串行、按模型输出顺序**：查工具、`prepareArguments`、schema 校验、`beforeToolCall` 钩子逐个跑。校验失败/被 block 的调用当场变成错误结果（"immediate" 分支），不进入执行阶段。
2. **执行并发**：通过 preflight 的调用各自异步执行，`tool_execution_end` 事件按**完成顺序**发出（UI 能实时看到谁先跑完）。
3. **结果回填按源顺序**：最后 `Promise.all` 收齐后，ToolResultMessage 严格按 assistant 消息里 toolCall 的**原始顺序**追加进上下文——保证发给 LLM 的历史顺序稳定，与执行快慢无关。

### 1.4 并行下的写冲突保护：按文件粒度的互斥队列

工具层还有一道保护：`coding-agent/src/core/tools/file-mutation-queue.ts:32` 的 `withFileMutationQueue`。edit 等写文件的工具会把操作挂到以 `realpath`（解析符号链接后的真实路径）为 key 的 promise 链上——**同一个文件的写操作串行化，不同文件仍然并行**。这样模型并行发两个 edit 也不会把同一个文件写花。

### 1.5 串行模式下的 abort 行为

串行执行时每做完一个调用检查 `signal.aborted`，中断则跳出循环（agent-loop.ts:477-479）——**已开始的调用有完整结果，未开始的调用不留半截状态**，剩下的孤儿 toolCall 交给第 6 层的上下文自愈兜底。

## 2. 容错第 1 层：流式 JSON 三级抢救

文件：`packages/ai/src/utils/json-parse.ts`

模型流式输出的工具参数 JSON 经常是坏的（未闭合、含裸控制字符、非法转义）。pi 的 `parseStreamingJson` 按顺序试三招，**保证永远返回一个对象，绝不抛异常**：

```
① JSON.parse                      标准解析
② repairJson 后再 parse           修复字符串字面量：
                                    · 字符串内裸控制字符（裸换行/Tab）→ 转义为 \n \t \uXXXX
                                    · 非法转义符（\x 等）→ 反斜杠双写救回
                                    · 残缺 \u 序列 → 双写反斜杠
③ partial-json 库部分解析          截断的 JSON 也能解出已完整的字段
   （原文/修复后各试一次）
④ 兜底                            返回空对象 {}
```

这个解析器有两个用途：流式期间实时解析参数（供 UI 渲染工具调用预览），以及消息终结时的最终参数定稿。

**注意副作用**：正因为③的抢救能力太强，被 token 上限截断的参数也可能"成功"解析出一个残缺但合法的对象——这个隐患由第 5 层的 length 防御专门堵住（见 5.2）。

## 3. 容错第 2 层：参数校验——先强转再校验，失败信息当提示词写

文件：`packages/ai/src/utils/validation.ts`（入口 `validateToolArguments`，:278；由 agent-loop.ts:617 调用）

### 3.1 校验前的双向类型强转（coercion）

弱模型最常见的错误是参数类型不对（数字发成字符串、布尔发成 0/1）。pi 在 TypeBox schema 校验**之前**先做两轮强转：

1. `Value.Convert(tool.parameters, args)` —— TypeBox 内置转换
2. 自研的 `coerceWithJsonSchema`（针对非 TypeBox 的裸 JSON Schema，如扩展/MCP 工具）：
   - `"5"` → `5`（number/integer）、`"true"` → `true`、`1` → `true`
   - `null` → 该类型的零值（`0` / `""` / `false`）
   - 反向也转：数字/布尔 → 字符串
   - `anyOf`/`oneOf` 联合类型：**深拷贝后逐个分支试转，用哪个分支能通过校验就用哪个**
   - 对象/数组递归下钻，`additionalProperties` 也处理

大部分类型错误在这里被无声救回，**根本不消耗一轮重试往返**。

### 3.2 校验失败的错误消息是三段式"重试指导"

强转后仍不过，抛出的错误（会被第 4 层 catch 成 toolResult 回给模型）长这样：

```
Validation failed for tool "edit":
  - edits.0.oldText: Expected string

Received arguments:
{
  "path": "src/foo.ts",
  "edits": [{ "oldText": 123, "newText": "bar" }]
}
```

字段路径（`instancePath` 转成点号路径，required 错误会拼出缺失字段的完整路径）+ 期望什么 + **模型实际发来的完整参数原样附上**。模型对着自己刚发的东西改，一轮就能纠正。

### 3.3 编译缓存

schema 编译过的 validator 用 `WeakMap` 缓存（validation.ts:6），每轮调用不重复编译。

## 4. 容错第 3 层：调用准备（preflight）——幻觉工具名、参数归一化、拦截钩子

文件：`packages/agent/src/agent-loop.ts:599-663`（`prepareToolCall`）

preflight 按顺序做四件事，任何一步失败都返回 "immediate" 错误结果（不执行、不抛异常）：

### 4.1 工具查找

模型幻觉出不存在的工具名 → 直接返回 `Tool ${name} not found` 的错误 toolResult。循环继续，模型下一轮看到错误自己改。

### 4.2 prepareArguments：工具自带的"模型怪癖归一化"钩子

每个工具可选实现 `prepareArguments(rawArgs)`，在校验**之前**修理参数。edit 工具的实现（`coding-agent/src/core/tools/edit.ts:94-118`）是最好的范例，注释直接点名肇事模型：

```ts
// Some models (Opus 4.6, GLM-5.1) send edits as a JSON string instead of an array
if (typeof args.edits === "string") {
    try {
        const parsed = JSON.parse(args.edits);
        if (Array.isArray(parsed)) args.edits = parsed;
    } catch {}
}
```

外加旧版扁平格式兼容：模型发 `{path, oldText, newText}`（不带 edits 数组）→ 自动折叠成 `{path, edits: [{oldText, newText}]}`。

**设计要点：归一化逻辑放在工具定义里而不是循环里**——每个工具最清楚模型会怎么发错自己的参数，循环层保持通用。

### 4.3 schema 校验

调第 3 节的 `validateToolArguments`，失败 → 错误结果。

### 4.4 beforeToolCall 钩子（权限门控的挂载点）

校验通过后调 `config.beforeToolCall`，返回 `{block: true, reason}` 即拦截 → 错误结果（内容为 reason）。coding-agent 把扩展系统的 `tool_call` hook 接在这里（`agent-harness.ts:420-428`），权限确认、路径保护等扩展都走这个口。

preflight 全程还穿插 `signal.aborted` 检查，中断时返回 "Operation aborted" 错误结果。

## 5. 容错第 4 层：执行期——异常捕获、截断防御、abort 收尾

### 5.1 execute 异常 → 错误结果

`agent-loop.ts:665-706`（`executePreparedToolCall`）：`tool.execute()` 抛任何异常都被 catch 成：

```ts
{ content: [{ type: "text", text: error.message }], isError: true }
```

工具作者可以放心 `throw new Error("给模型看的错误信息")`——错误消息本身就是回给模型的内容。流式进度回调（onUpdate）在结束/异常后立刻停止接收，避免迟到的更新事件乱序。

### 5.2 stopReason="length" → 整批工具调用拒绝执行 ⭐

`agent-loop.ts:206-213` + `failToolCallsFromTruncatedMessage`(:380)：

assistant 消息因 **token 上限被截断**（stopReason="length"）时，消息里的每个 toolCall 都**不执行**，统一返回错误结果：

> Tool call "xxx" was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.

源码注释讲清了动机：因为第 1 层的抢救式解析太强，截断的参数**能解析、能过校验，但内容是静默不完整的**（比如 edit 的 newText 少了后半截，写进文件就是事故）。所以只要消息被截断，一律拒执行、让模型重发。这是"抢救式解析"必须配套的安全阀。

### 5.3 输出截断：双限制 + 全量落盘

`packages/agent/src/harness/utils/truncate.ts`：

- 两个独立限制，**先到先截**：2000 行 / 50KB
- 永不截半行（除 bash 尾部截断的边缘情况）
- bash 工具截断时把**全量输出写到磁盘文件**，toolResult 里附路径：`[Output truncated. Full output: /path/to/file]`——模型需要时自己用 read/grep 去翻，而不是彻底丢失信息
- grep 每行匹配还有 500 字符的单行上限

### 5.4 afterToolCall 钩子与 terminate

`agent-loop.ts:708-753`（`finalizeExecutedToolCall`）：执行完后 `afterToolCall` 钩子可以改写结果（content/isError/usage/terminate）；**钩子自己抛异常也被 catch 成错误结果**。工具结果可携带 `terminate: true`，整批全部 terminate 时循环终止（`shouldTerminateToolBatch`，:581）——给"任务完成类"工具留的退出口。

## 6. 容错第 5 层：发给 LLM 前的上下文自愈 ⭐⭐

文件：`packages/ai/src/api/transform-messages.ts:158-223`

**这是全链路里最值得抄的一层。** 每次向 LLM 发请求前，对整个消息历史做一遍修复扫描（两趟遍历）：

### 6.1 丢弃残缺的 assistant 消息

```ts
// transform-messages.ts:189-197
// Skip errored/aborted assistant messages entirely.
// These are incomplete turns that shouldn't be replayed:
// - May have partial content (reasoning without message, incomplete tool calls)
// - Replaying them can cause API errors (e.g., OpenAI "reasoning without following item")
if (assistantMsg.stopReason === "error" || assistantMsg.stopReason === "aborted") {
    continue;
}
```

### 6.2 孤儿工具调用自动补合成结果

崩溃、打断、丢弃残缺消息之后，历史里会出现"有 toolCall 没 toolResult"的孤儿。扫描逻辑在三个时机补上合成结果：

- 下一条 assistant 消息出现前
- user 消息插队打断工具流时
- 整个历史结尾

合成结果长这样：

```ts
{
    role: "toolResult",
    toolCallId: tc.id,
    content: [{ type: "text", text: "No result provided" }],
    isError: true,
}
```

### 6.3 关键取舍：修复只发生在请求边界

session 里的原始历史**原样保留**（错误消息、残缺轮次都在，供 UI 展示和 /tree 回溯）；修复是发请求前的一次性视图变换。效果：**无论历史被打断/崩溃弄得多烂，发出去的请求永远是合法结构**——这远比"在每个打断点小心翼翼维护状态一致性"简单可靠。

（同文件的第一趟遍历还做跨模型换模时的 toolCallId 归一化、剥离其他家的 thoughtSignature——provider 兼容层的内容，本报告不展开。）

## 7. 容错第 6 层：API 层错误——错误即数据 + 白名单重试 + 溢出分流

### 7.1 错误即数据

pi-ai 的流式调用**不向上抛异常**：API 报错、断流、超时都物化成一条 `stopReason: "error"`（附 errorMessage）的 assistant 消息；用户打断则是 `stopReason: "aborted"`。主循环看到这两种 stopReason 就发 `turn_end`/`agent_end` 干净退出（agent-loop.ts:195-199）。错误进入消息流而不是控制流，所以能被 session 持久化、被 UI 渲染、被下面的重试逻辑消费。

### 7.2 重试判定：正则白名单 + 黑名单优先

文件：`packages/ai/src/utils/retry.ts:97`（`isRetryableAssistantError`）

- **黑名单先行**（命中即不重试）：配额耗尽（insufficient_quota）、账单问题（billing）、订阅限额（Monthly usage limit reached）——重试也没用的错误明确排除
- **白名单**（命中才重试）：429/5xx/524、overloaded、rate limit、各种网络断流（socket hang up、fetch failed、connection refused）、SDK 断流（"stream ended before message_stop"）、provider 明示重试（"you can retry your request"）等
- 每条 pattern 都注释了对应的真实 issue 编号（#733、#2264、#3317、#4433、#6019...）——**这个清单是踩坑攒出来的，不是设计出来的**，直接抄等于白得别人的生产事故经验

分层也讲究：pi-ai 只提供**判定函数**，不做重试策略；退避、预算、上报由上层自选。

### 7.3 重试执行：会话层的指数退避

文件：`packages/coding-agent/src/core/agent-session.ts:2609-2701`

- 延迟 = `baseDelayMs × 2^(attempt-1)`，有 maxRetries 上限，等待期可被用户 abort
- **重试前把错误 assistant 消息从 agent 工作状态里移除**（session 历史保留），然后用 `agentLoopContinue` 从上一个合法状态续跑
- 一旦拿到成功的 assistant 响应，重试计数立即归零

### 7.4 上下文溢出单独分流

`agent-session.ts:1928` 起：上下文溢出错误**不走重试**（重试也必然再溢出），而是：移除错误消息 → 自动压缩（compaction）→ 自动续跑；只给一次机会，压缩后仍溢出则报错并提示用户换大上下文模型。阈值触发的预防性压缩（还没溢出但快了）则只压缩不自动续跑。

## 8. 容错第 7 层：工具内部的自救（以 edit 为例)

循环层的机制之外，内置工具自己还有一层容错，`edit` 最典型（`coding-agent/src/core/tools/edit-diff.ts`）：

- **精确匹配失败 → 降级 fuzzy 匹配**（:206 `fuzzyFindText`）：把文件内容和 oldText 都做归一化（去每行行尾空白）后再找。模型抄代码时最容易丢的就是行尾空格，这一步救回大量本要失败的 edit
- **错误消息全部是行动指导**（:257 起）：
  - 找不到 → "Could not find edits[2] in path. The oldText must match exactly including all whitespace and newlines."
  - 多处匹配 → 指出出现了 N 次，要求提供更多上下文使其唯一
  - 空 oldText、替换后内容无变化，各有专门的错误文案
- BOM 剥离后再匹配（模型不可能在 oldText 里带上不可见的 BOM）、CRLF/LF 归一化后再还原——消灭两类"模型不可能对齐"的隐形差异

bash 工具则是：timeout 参数校验（非法值直接报错给模型）、超时 kill 后报 `timeout:N`、退出码非零如实回传（exitCode 进 toolResult，但**非零退出码不算 isError**——命令跑完了就是有效结果，让模型自己解读）。

   ▼

## 10. 对哒哒 Agent Core 的启发

结合 9b/1.7b 弱模型 + Ollama 的场景，按性价比排序：

1. **L2 参数强转（validation.ts 的 coercion）**：弱模型类型错是高频错误，强转直接救回、不消耗重试往返——对延迟敏感的语音场景价值最大。
2. **错误消息当提示词写**：所有工具错误统一按"字段路径 + 期望 + 附原始参数 + 下一步怎么改"的格式设计，和 L2 提示词"救回段"思路同构，可纳入消融实验。
3. **上下文自愈（transform-messages）**：pending/打断机制迟早制造孤儿 toolCall；在**请求边界统一修复**比在每个打断点维护状态简单一个量级。
4. **length 拒执行**：成本极低的一条 if，堵住"截断参数被抢救解析后静默执行"的事故通道，建议直接抄。
5. **重试白名单**：retry.ts 那份带 issue 编号的正则清单可以直接搬，等于白得别人的生产事故经验。
6. **多工具并行的三段式**（串行 preflight → 并发执行 → 按源顺序回填）：哒哒短期用不上并行，但"结果顺序与执行快慢解耦"的原则在任何异步工具场景都适用。
